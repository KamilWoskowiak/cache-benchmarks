Coding Style
------------

In general, we follow the [C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines). Some of these guidelines are checked by `clang-tidy`.

Additional conventions are listed below.

### Naming

We follow the STL naming conventions. In general:

* Macros are written using `UPPER_SNAKE_CASE`.
* Template parameters are written using `UpperCammelCase`.
* All other names, including types, functions, variables, and concepts, are written using `lower_snake_case`.

We use these conventions for type aliases:

* Non-member type aliases are named with the suffix `_t`.
* Member type alias are named with the suffix `_type`.

We use these conventions for member variables and member functions:

* Private member variables are named with the suffix `_`.
* Private member functions are named with the prefix `m_` and the suffix `_`.

Additionally:

* Only macros should be defined in the global namespace.
* Everything else should be defined in the `alc` namespace.
* All macros should be named with the prefix `ALCAMI_`.

### Include Guards

An include guard for a file named `filename.h` should follow the format `ALCAMI_[MODULE]_FILENAME_H`, where `[MODULE]` refers to the "part" of the project that the file is from. We do not have specific rules for what `[MODULE]` should be, but here are some examples:

* A file in `include/alcami` should be named `ALCAMI_INCLUDE_FILENAME_H`.
* A file in `src` should be named `ALCAMI_SOURCE_FILENAME_H`.
* A file in `tools` should be named `ALCAMI_TOOLS_FILENAME_H`.

### Formatting

For C++, we use `clang-format` and provide a `.clang-format` file based on the LLVM formatting style. For CMake, we use `cmake-format` and provide a `.cmake-format.json` file.

Libraries

We make liberal use of the following libraries:

* Boost: Feel free to use any boost project.

* spdlog: Use for logging.

Scripts
-------

We provide scripts that simplify (and document) some development workflows, such as configuring CMake, running tests, etc. These scripts are located in the `scripts/` directory.

Here is a summary of the scripts you might want to use.

* `scripts/configure [PRESET]`: Configures CMake with some preset options. Run without arguments to see all presets.
* `scripts/configure develop`: Configures CMake with this project's default development options.
* `scripts/build`: Runs the build system's default target(s).
* `scripts/install`: Runs the build system's install target.
* `scripts/clean`: Runs the build system's clean target.
* `scripts/hard-clean`: Removes all files generated by CMake and the build system.
* `scripts/coverage`: Runs the build system's code coverage target.
* `scripts/options`: Prints the configurable CMake cache variables and their current contents.
* `scripts/edit-cache`: Starts `ccmake` (the CMake TUI).
* `scripts/test-all`: Uses CTest to run unit and integration tests.

For scripts that call CMake, those scripts forwards any additional arguments to the CMake call.

Version Control
---------------

If you have environment-specific files that shouldn't be checked into version control (e.g., from your editor, operating system, etc.), add those files to your `.git/info/exclude` instead of `.gitignore`.

Adding Files
------------

Make sure that `src/alcami.cpp` includes _all_ header files in `include/` and `src/`. This is to make sure that analysis tools can find all the header files. Public header files should be added to `include/alcami/alcami.h`, which is included by `src/alcami.cpp`.

Testing
-------

### Terminology

For testing _units of code_, we consider two broad categories of tests: _unit tests_ and _integration tests_. We define these categories follows.

**Unit Tests.** A unit test is a test for one or more units of code that

1. focuses primarily on a single unit of code,
2. is fast to execute, and
3. does not require external setup.

**Integration Tests.** An integration test is a test for one or more units of code that either

1. focuses on the combination of multiple units of code,
2. is slow to execute, or
3. requires external setup.

We use the `GoogleTest` framework for unit and integration tests.

### Running Tests

Unit tests are located in `test/unit`, and integration tests in `test/integration`. The executable for unit tests is named `alcami-unit-tests`, and that for integration tests is named `alcami-integration-tests`.

To enable building tests, configure CMake with the `-DALCAMI_BUILD_TESTS=1` option.

The script `scripts/test-all` will use `ctest` to run tests.

### Adding Tests

Add a file with the `_test.cpp` suffix in the corresponding directory, and add it to the corresponding target in the CMakeLists.txt.

Static Analyzers
----------------

We use `clang-tidy` for static analysis, and we provide a `.clang-tidy` configuration file.

You can configure CMake to run `clang-tidy` at build-time by using the `-DALCAMI_ENABLE_CLANG_TIDY=1` option (or use `scripts/configure analyze`). Keep in mind that this will slow down compilation.

Sanitizers
----------

You can configure CMake to build with sanitizers by using the `-DALCAMI_ENABLE_SANITIZER_ADDRESS=1`, `-DALCAMI_ENABLE_SANITIZER_MEMORY=1`, `-DALCAMI_ENABLE_SANITIZER_UB=1` and/or `-DALCAMI_ENABLE_SANITIZER_THREAD=1` options. (Some combinations of sanitizers are incompatible with each other.)

Code Coverage
-------------

We use `gcov` and `lcov` to generate code coverage reports. To enable the code coverage build target, configure the build system with the `-DALCAMI_ENABLE_COVERAGE` option (or use `scripts/configure coverage`). Then build the `alcami-code-coverage` target (or use `scripts/coverage`).

Documentation
-------------

To enable the doxygen build target, configure the build system with the `-DALCAMI_BUILD_DOXYGEN=1` option. Then to generate the documentation, build the `alcami-doxygen` target (or use `scripts/doxygen`).
